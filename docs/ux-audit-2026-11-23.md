# Audit UX/UI & accessibilité — BabelGrade (2026-11-23)

> Audit live de l'app (serveur :8090, commit `a6281f8`), desktop 1280px + mobile 390px (iPhone, FR),
> 23 captures + sondes DOM/accessibilité. **Document interne — NON exposé sur le site public**
> (le site GitHub Pages ne le référence pas ; `build_site.py` inchangé).
> Contexte : l'app est utilisée **potentiellement en 3 sessions simultanées** —
> mobile (photo des copies, validation critère par critère) + desktop (tâches, classes,
> stats, exports). Ce prisme guide la priorité de la Vague 5.
>
> Méthode : captures Playwright (FR forcée via `babelgrade-lang`), relecture visuelle +
> re-vérification par le code pour chaque constat (règle : une capture ne prouve pas un bug —
> le code tranche). Contrastos mesurés par calcul WCAG (formule relative-luminance).

## 0. Ce qui va bien (à ne pas toucher)

- **0 erreur JS** sur les parcours complets desktop et mobile.
- Le **mode Évaluation critique par critique** mobile (landscape) est solide : cartes côte à côte,
  diff word-level, chips d'écart, sortie propre (exit-bar dirty/clean, popstate consommé).
- Le **bottom sheet de niveau** (P2.2) a un grab handle, des boutons ≥48px, option Effacer.
- La **nav mobile** (bottom tab bar) a des cibles 44px+ et un indicateur d'onglet actif.
- Les **marqueurs de champs requis** (P0.5) sont présents avec flash + toast + scroll.
- La **grille i18n** et le cache-busting no-cache (2026-11-23) sont en place.
- Le rapport desktop est dense mais **structuré** (essentials → attestation → IA → transcription →
  points forts → feedback), ce qui est le bon contrat « preuve ».

## 1. Bugs réels (P0 — corriger d'abord)

### B1. Pastille de niveau « vide » dans le bottom sheet (mobile)
**Symptôme** : quand le niveau courant d'une ligne est **B2**, le bouton correspondant dans
`#lvl-sheet` affiche une capsule bleue **sans texte** (captures `lvl_sheet_mobile.png`).
L'enseignant ne peut pas relire le niveau qu'il est en train de manipuler.
**Cause** (vérifiée dans `static/index.html`) : `.lvl-sheet-btn.on .ls-lv{color:var(--acc)}`
force le texte en `--acc` (bleu `#2563eb`) dans l'état `.on`, alors que le span porte aussi
`.level.B2` dont le fond est `#2563eb` → texte bleu sur fond bleu. Le problème existe pour
**tout niveau dont la couleur = `--acc`** (B2) ; les autres niveaux changent de teinte mais
conservent un lisible (à auditer).
**Fix** : dans l'état `.on`, ne toucher qu'à la bordure/fond du bouton — laisser `.ls-lv`
rester au style `.level.<Lv>` (texte blanc). 1 règle CSS + test E2E (assert `getComputedStyle`
du `.ls-lv` sélectionné = blanc, ratio ≥ 4.5).

### B2. Piège de focus des modales non fonctionnel (desktop)
**Symptôme** (sonde live) : à l'ouverture de la modale « détail sujet », `activeElement` est
**hors du dialogue** (`activeInDialog:false`) et 6 pressions Tab ne font jamais entrer dans
le dialogue (cycle : bouton de fond ×6). Pas de focus initial, pas de piège.
**Impact** : clavier = impossible de parcourir le contenu d'une modale (WCAG 2.4.3).
**Fix** : au `show`, focus le premier élément focusable (ou le titre `tabindex="-1"`) ;
piéger Tab/Shift+Tab dans le dialogue ; au close, restaurer le focus sur le déclencheur.
Appliquer à : `#assignment-detail-overlay`, `#assignment-edit-overlay`, `#confirm-dialog`,
`#lvl-sheet`, `#eval` (+ sortie propre déjà gérée), `#roster-overlay`.

### B3. Contraste des pastilles de niveau (mesuré, blanc sur fond)
| Niveau | Fond actuel | Ratio | AA (4.5) |
|---|---|---|---|
| A1 | `#16a34a` | 3.30 | ❌ |
| A2 | `#0d9488` | 3.74 | ❌ |
| B1 | `#0ea5e9` | **2.77** | ❌ (pire) |

Les pastilles sont le **code couleur de l'outil** (niveaux CEFR partout : rapports, stats,
évaluations) — le texte y est 12.5px/700. **Fix proposé** (teintes 700, mesurées) :
A1 → `#15803d` (5.02), A2 → `#0f766e` (5.47), B1 → `#0369a1` (5.93). Impact global :
changer les 3 variables CSS (`--lvl-a1`, `--lvl-a2`, `--lvl-b1`) + vérifier les 2nd niveau
(les badges `.badge` bleus : 4.75 ✅ juste).

## 2. Accessibilité structurelle (P1)

### A1. `<html lang="en">` figé
L'UI peut être FR/ES/DE mais l'attribut `lang` reste `en` → lecteurs d'écran qui lisent le
français avec des règles anglaises. **Fix** : `applyI18n()` fait
`document.documentElement.lang = LANG` (1 ligne, 4 langues → `fr|es|de|en`).

### A2. Zéro `aria-live`
Les toasts (`#toast`, ~10 sites) sont silencieux pour les lecteurs d'écran ; idem pour le
chip d'exécution en cours (`#run-chip`). **Fix** : `#toast` = `role="status" aria-live="polite"` ;
`#run-chip` = `aria-live="polite"` sur le seul champ qui change (phase).

### A3. 132 boutons sans nom accessible (sur 430)
Les boutons icon-only (toolbar élèves, actions de lignes, `#ev-close` dont le `title` est
littéralement `"✕"`) ne sont pas nommés. **Fix** :
- `title`/`aria-label` i18n ×4 sur chaque bouton icon-only (remplacer les `title="✕"` par
  `aria-label=t('a11y.close')` etc.) ;
- auditer les boutons générés en template (actions de lignes : 📊 👁 ▶ ✎ ✕).

### A4. Focus invisible sur les éléments clés
`outline:none` sur les secteurs du menu radial + nav (mesuré : `outlineWidth 0px` sur les
boutons `#nav` au focus). **Fix** : règle globale `:focus-visible{outline:2px solid var(--acc);
outline-offset:2px}` + retirer les `outline:none` ciblés (garder `.rsvg .sector:focus` avec un
style alternatif visible, ex. `filter:drop-shadow`).

### A5. Le menu radial (Home) est inatteignable au clavier
Les 3 verbes L0 (Évaluer/Analyser/Préparer) sont `tabindex="-1"` ; seul le centre
(« Fermer le menu ») est focusable. L'écran d'accueil est donc **non navigable au clavier** —
et c'est le boot par défaut. **Fix (minimal)** : mettre le `#pie-wrap` en `tabindex="0"` +
rôles (`role="menu"` sur la couronne, `menuitem` déjà présents sur les `<g>`) + flèches
déjà gérées par `rCycle`/`rExecute` (il suffit de relier `keydown` au focus du wrap).
Option plus complète : roving tabindex + aria-selected (Vague 2b).

### A6. Champs de formulaire sans `<label>` associé
`#assignment`, `#student`, `#rubric`, `#title`, `#accommodations`, `#eval-notes` : labels
visuels non associés (sonde : `labels.length === 0`, pas d'`aria-label`). **Fix** :
`<label for="…">` sur les 6 champs (les labels existent déjà visuellement — c'est de la
reliation, pas du design) + `aria-required` sur les 2 requis.

### A7. Tableaux sans `th scope` / caption
`#hist` : 9 `th` sans `scope="col"`, pas de caption. **Fix** : `scope` sur tous les `th`
(généré au template) + `caption` i18n. Même traitement pour les tables des vues Stats.

### A8. Pas de `prefers-reduced-motion`
21 règles transition + 7 animations + l'icône de rotation qui tourne en boucle. **Fix** :
`@media (prefers-reduced-motion: reduce){ *{animation:none!important; transition:none!important} }`
(+ garde sur l'animation du hint rotation qui devient statique).

### A9. Champs requis signalés par couleur seule
L'astérisque rouge (P0.5) + le `.req-flash` sont visuels seulement. **Fix** : ajouter
« (obligatoire) » dans le texte du label requis (ou `aria-describedby` vers le `.reqNote`
existant) — la couleur ne doit pas être le seul signal (WCAG 1.4.1).

## 3. Ergonomie — mobile (photo + validation critère par critère)

### M1. « Critère par critère » = rotation obligatoire en portrait
Choix de design documenté (3 colonnes → paysage), le hint plein écran a son propre ✕ et le
flux de sortie fonctionne (P7). MAIS pour l'usage « valider sur le vif en salle de classe »,
la rotation physique est une friction majeure (une main tient le téléphone, l'autre tape).
**Option** : layout **portrait natif** (1 critère plein écran, les 6 niveaux en grille 3×2
comme le bottom sheet, diff compact sous le niveau sélectionné). Effort moyen — le moteur
`evRender()` est déjà responsive (il bascule 3col↔scale à 900px, il suffit d'un 3ᵉ mode
`<480px portrait`).
→ **Décision à prendre ensemble** : on garde le paysage (comportement connu, testé) ou on
ajoute le portrait natif ? C'est le seul point mobile « bloquant » de ton usage.

### M2. Pas d'accès direct à l'appareil photo
Les inputs photo (`accept="image/*"`, copies + consignes + document) n'ont **pas**
`capture="environment"` → sur mobile, l'utilisateur tombe sur le picker générique
(galerie/fichiers/caméra) au lieu de l'appareil photo directement.
**Fix** : `capture="environment"` sur l'input des copies (et optionnellement consigne/document) —
1 attribut. Nuance : certains navigateurs avec `capture` ne permettent plus la galerie →
comportement à valider sur tes téléphones (test manuel).

### M3. Le CTA « Évaluer » vit dans le header mobile
Sur 390px, l'action principale est en haut (header sticky), loin de la fin du formulaire ;
le pied du formulaire n'a pas de barre d'action sticky mobile (le `.card.an-actions` sticky
existe côté desktop). **Fix** : rendre `.an-actions` sticky-bottom sous 760px (le CSS existe
départiellement — à vérifier sur le vrai mobile, capture `evaluator_top_mobile.png` montre le
CTA en header uniquement).

### M4. Densité de la liste mobile
La carte hcard du détail mobile est correcte, mais la page de détail est **très longue**
(captures : 13 sections). L'ordre actuel (photos → synthèse → attestation → IA →
transcription → points forts → axes → feedback → 5 boutons) demande beaucoup de scroll
avant d'atteindre l'essentiel (niveau + score). **Option** : sticky « essentials » en haut
(le bandeau att-ess existe déjà desktop) + repli des sections photo/transcription derrière un
`<details>` ouvert.

## 4. Ergonomie — desktop (tâches, classes, stats, exports)

### D1. 2 CTA quasi identiques : « Analyser avec l'IA » vs « Évaluer d'abord »
Deux boutons solid blue qui diffèrent par teinte, sans tooltip. Risque de mauvais clic sur
l'action qui **coûte 60–130 s**. **Fix** : tooltips i18n explicatifs + différencier le
second en `ghost` (ou inversement : 1 seul bouton principal, l'autre secondaire) + 1 ligne
d'aide sous les boutons (le footer « Required : … » existe déjà, l'étendre).

### D2. 5 boutons icon-only par ligne de sujet
Cluster 📊 👁 ▶ ✎ ✕ en 2×2+1 irrégulier, tooltips uniquement (pas de labels). **Fix** :
labels courts (comme P3.2 l'a fait pour la toolbar élèves) ou minimum `aria-label` ×4 +
régulariser le cluster (5 boutons en 1 ligne, wrap si besoin).

### D3. Wizard trompeur
Le stepper « Sujet / Élève & niveau / Travail / Grille » suggère du séquentiel, mais les 4
cartes sont toutes visibles/éditables ; la pastille « active » ne correspond pas au contenu
écran (le scroll-spy marque `.on` au défilement, mais sans Next/Back et sans ✓ de complétion,
la métaphore est inachevée). **Options** :
- (a) basculer en vrai wizard 1 étape à la fois (gros effort, casse les flux rapides) ;
- (b) garder le formulaire continu et **renommer** le stepper en « sommaire » avec ✓/●/○
  (complet / en cours / vide) — léger, honnête, le scroll-spy existe déjà.
→ Recommandation : (b).

### D4. Toolbar dense & boutons opaques
« ◀◀ Simplifié » (id `hdr-home`, toggle home) et « ⚙ Données » manquent de contexte ; la
pastille « Whisper base » est affichée même sans audio. **Fix** : tooltips ×4 sur les 2
boutons ; cacher la pastille Whisper quand la tâche est écrite (ou la rendre `muted`).

### D5. Petits défauts visuels (tableau Sujets)
- colonne DEPUIS : date sur 2 lignes (largeur de colonne) ;
- PRODUCTIONS : le souligné pointillé (affordance de scroll) rogne les chiffres ;
- ressources : badges inconsistants (« photos 1 » = count, « Consigne » = catégorie) —
  homogénéiser en « 📷 1 photo » / « ✏️ Consigne » etc.

## 5. Concurrency — 3 usages simultanés (le point que tu signalais)

### C1. SQLite en mode `delete` (pas WAL)
`PRAGMA journal_mode` = `delete`, `busy_timeout` = 5000ms. En écriture, le fichier est
verrouillé pour **tous** les connexions → 3 sessions qui sauvegardent en même temps
s'exposent à « database is locked » (timeout 5 s). **Fix** : `PRAGMA journal_mode=WAL` à
l'`init_db` (persistant, réversible, zéro autre changement). WAL = lectures concurrentes
libres + écriture unique avec file d'attente correcte.

### C2. File de jobs LLM à 1 worker
`MAX_WORKERS = 1` (cap 4) dans `app/jobs.py`. 3 « Analyser avec l'IA » simultanés se
**sérialisent** : le 3ᵉ attend ~3–4 min. Pour l'usage simultané : monter `max_workers` à
3–4 (mémoire : chaque job = 1 appel LLM SGLang, pas de mémoire lourde côté app — le
goulot est le LLM lui-même, à vérifier sa capacité à 3–4 requêtes concorrentes).
**UI associée** : le chip `#run-chip` et la vue Tâches doivent montrer la **position dans la
file** (job n°X, en attente / en cours / terminé) pour que 3 utilisateurs comprennent
l'état. La table `jobs` + le SSE existent — c'est du rendu.

### C3. Lecture vs écriture (faible priorité)
L'usage réel (mobile = écrire/valider, desktop = lire/stats/exports) est majoritairement
lecture côté desktop → WAL (C1) suffit ; le reste n'a pas besoin d'infra.

> ⚠️ Limite de l'audit : je n'ai pas **saturé** la base avec 3 clients (test de charge) —
> le constat C1 est structurel (mode journal), le risque est avéré mais non reproduit.
> Proposition : un mini-script de charge (3 PUT concurrents) comme preuve avant/après WAL.

## Annexe — Constats écartés (fausses alarmes vérifiées)
- « Tab bar qui recouvre le contenu mobile » dans les captures full-page = **artefact
  screenshot** (les `position:fixed` se répètent à chaque tranche de viewport). Vérifié par
  capture viewport + `elementFromPoint` : aucun recouvrement réel.
- La synthèse/le feedback IA en anglais dans un rapport FR = **donnée générée avec
  `ui_language=en`** au moment de l'analyse (comportement par design : la langue UI active
  au moment de l'appel pilote la sortie IA). À ne pas confondre avec un bug i18n — mais
  c'est un **point d'ergonomie légitime** (remarque : relancer l'IA en FR régénère en FR).
- Le hint « Tournez votre téléphone » qui n'apparaissait pas sur une capture = artefact de
  contexte Playwright ; reproduit correctement sur contexte mobile `pointer:coarse`
  (capture `eval_rotate_hint_mobile.png`).
