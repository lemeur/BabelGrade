Architecture — module map & conventions

One-page map of the codebase (2026-10-16 module split) so a new contributor — or a future agent session — can navigate without re-discovering. Companion docs: Async jobs (deep dive on the job queue) and the README (features).

Import direction is one-way and layered: db <- {stats, media, jobs, …} <- routes <- main (the UI talks to main only, via /api/*). Never create the reverse — e.g. a db.py re-export of the stats.py names would make db <-> stats circular (hit in P2.7). The table above carries the per-module "calls which" detail; the diagram carries the layering.

Long-endpoint request lifecycle

The three heavy endpoints (POST /api/analyze, POST /api/evaluate, POST /api/analyses/{id}/run-ai) are async: the request stages uploads fast, persists rows, enqueues a job and returns a job handle. Progress is followed on GET /api/jobs/{id}/events (SSE: meta → phase* → token* → result → done|error|cancelled). Full state machine + sequence detail: the Async jobs doc.

Conventions to preserve

  • Owner scoping — every owned row carries owner_id; the request's identity rides in auth.owner_var (a contextvar) and db._owner() reads it. Job runners re-set it per job. New owned queries MUST filter by it (or use a _scoped() helper).
  • Proof-matrix rule — every rubric criterion gets a mapping with at least one verbatim evidence item; assess.validate_matrix() warnings are surfaced in the UI. No level without a quote/timestamp.
  • Media ownership — /api/files serves a file only to its owner (db.media_owner_map()); untracked files 404.
  • Last AI opinion wins — run-ai overwrites analyses.ai_matrix_json on every run; matrix_json is the teacher's, never touched by the AI.
  • No per-element listeners inside a rendered report — the history flow re-serialises #hist-report via innerHTML, which detaches them. All report interactivity is document-level delegation registered once at boot.
  • Never bind a local named t, esc, stats, $ in a function that also needs the global of that name — the i18n t shadowing cost a whole debugging session; stats is the module, so local vars are data/agg.
  • i18n — every key exists in all 4 languages (en/fr/es/de); FR values use typographic apostrophes (') only; run the 4-way key-count check after any i18n edit.
  • DB schema — forward-migrated at startup by init_db (idempotent ALTER TABLE ADD COLUMN); additive column changes need no manual migration.

Recipes

Add a new endpoint

  1. Put it in the matching app/routes_<domain>.py on that module's router (create a new module + include_router in main.py only for a genuinely new domain).
  2. Heavy work goes through a job (see Async jobs doc); light reads call db.* / stats.* directly.
  3. Owned data → scope with db._owner(); uploads → app/media.py helpers.
  4. UI: add the key(s) to all 4 i18n dicts + node --check the extracted JS.
  5. Add/extend a test in tests/ (in-process TestClient for API shape, Playwright for UI), commit, verify per the close-out checklist in https://github.com/lemeur/BabelGrade/blob/main/TODO.md.

Add a doc to the in-app Docs view

  1. Write docs/<name>.md (minimal markdown: headings, tables, fenced code, lists, quotes; mermaid fences render via the vendored mermaid).
  2. Add a slug to DOCS_INDEX in app/docs_catalog.py with its category (user or dev).
  3. i18n: add docs.tab.<slug> in all 4 languages.
  4. Frontend: the dev sub-tab labels come from an inline ternary in the docs view JS block (paintDocsSubtabs, static/index.html) that maps slugs to i18n keys — add your slug if its i18n key is not just the slug itself (architecture is the new case; async-jobs→asyncjobs).
  5. Verify in the app: Docs → Dev section → new sub-tab renders, mermaid diagrams paint (check visually, not just "it parsed").
